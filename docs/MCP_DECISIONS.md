# MCP 도입 판단

**기본값은 MCP 0개, 필요한 기능이 없을 때만 추가한다.** 이것은 점수 규칙이 아니라 설치·오류·외부 전송 부담을 줄이기 위한 제안이다. Skill은 풀이 방법을 제공하고, MCP는 실제 도구 접근을 제공하므로 별도로 판단한다.

## 후보별 결정

| 후보 | 도움을 기대하는 상황 | 대체 경로 | 현재 결정 |
|---|---|---|---|
| Playwright MCP | 로컬 웹앱의 클릭·입력·상태 전이를 에이전트가 직접 탐색해야 함 | 제공 미리보기, 기존 Playwright 테스트, CLI/스크립트 | 유일한 우선 검토 후보. 웹 과제일 때만 조건부 |
| Context7 | 생소한 라이브러리의 버전별 문서가 필요함 | 로컬 코드·설치 버전·허용된 공식 문서 읽기 | 기본 비활성. 일반 문서 질의만, 과제 내용 전송 금지 |
| Filesystem/Git MCP | 에이전트에 실제 파일·git 접근 능력이 없음 | 제공 터미널, 에디터, git CLI | 해당 능력이 이미 있으면 추가하지 않음 |
| SQLite/DB MCP | 주어진 DB를 반복적으로 탐색해야 하나 기존 접근 수단이 부족함 | sqlite CLI, Python, 기존 DB 클라이언트 | 간단한 CSV·로컬 앱 과제에서는 기본 제외 |
| 원격 검색·클라우드 DB·브라우저 서비스 | 과제에서 해당 서비스가 명시적으로 필요하고 허용됨 | 로컬 자료·제공 엔드포인트 | 사전 기본 구성에서 제외 |

## Playwright는 검수뿐 아니라 풀이 중에도 사용

예약 앱이라면 생성→충돌 시도→취소→재예약→새로고침을 실제로 수행해 구현을 수정하는 데 활용할 수 있다. 그러나 시간 구간 겹침이나 집계 계산은 함수 테스트로 더 간단히 확인할 수 있다. 화면 테스트와 로직 테스트의 역할을 구분한다.

Microsoft 공식 README는 코딩 에이전트에 CLI+Skills 방식이 더 적합할 수 있다고 설명한다. 따라서 MCP만 정답이라고 보지 않고 같은 시나리오에서 CLI와 비교한다.

### 사용 전 확인

- 현재 환경에서 실행 가능한 브라우저와 패키지가 있는가?
- 허용된 작업 공간 안의 본인 서비스만 조작하는가?
- 로컬 MCP가 외부 서비스에 데이터·로그·화면을 보내지 않는가?
- 페이지의 외부 폰트·분석기·이미지·스크립트가 불필요한 외부 요청을 만들지 않는가?
- 설치·설정 비용을 포함해도 기존 미리보기보다 도움이 되는가?

도구는 과제 서비스만 대상으로 한다. 감독 UI, 평가·관리 페이지, 개인 계정 브라우저에 연결하지 않는다. 화면 캡처나 산출물 저장도 실제 운영 규정이 허용하는 범위에서만 수행한다. 브라우저 MCP를 로컬로 띄웠다는 이유만으로 외부 전송이 없다고 단정하지 않는다.

Playwright의 allowed-origins 같은 옵션은 공식 문서에서 보안 경계가 아니라고 명시한다. 이 옵션만으로 외부 전송이 완전히 차단됐다고 주장하지 않는다.

## Context7의 주의점

공식 도구 스키마에서 query는 질문이나 과제를 담을 수 있는 인자다. 문제 원문, 파일 내용, 고유 데이터, 구현물, 키·토큰을 여기에 전달하지 않는다. `항상 Context7 사용` 같은 전역 자동 호출 규칙을 채택하지 않는다. 허용 여부가 불명확하면 비활성 상태를 유지한다.

일반 라이브러리 문서 질의의 예: `React controlled input의 초기값 처리`. 실제 과제의 요구사항과 코드를 포함한 디버깅 요청은 보내지 않는다.

## 호환성 계획

현재 저장소에는 자동 설치 스크립트나 활성 MCP 설정을 넣지 않는다. 실제 제공 버전에서 설정 형식·실행 옵션·프로세스 시작을 확인한 후 필요한 것만 고정한다. 최신 문서와 시험에 설치된 버전이 같다고 가정하지 않는다.

설정이 막히면 제한을 우회하지 않고 기존 터미널·미리보기·테스트로 전환한다. 제안하는 개인 설정 예산은 약 5분이며 공식 제한 시간이나 검증된 최적값은 아니다.
