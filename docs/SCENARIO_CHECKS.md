# Skill·MCP 시나리오 점검 계획

## 상태와 목적

아래는 **사전 설계·도상 점검**이다. 실제 에이전트 풀이, 브라우저 실행, MCP 연결, A/B 비교는 아직 수행하지 않았다. 기대 효과를 측정 결과로 표현하지 않는다.

목적은 스킬을 많이 모으는 것이 아니라, 같은 문제에서 **필수 요구사항 충족과 완성까지의 시간**에 도움이 되는 조합만 남기는 것이다. 실제 시험 문제가 아니라 독립적으로 만든 가상 과제만 비교에 사용한다.

## 비교 구성

| 구성 | 내용 | 구분하려는 효과 |
|---|---|---|
| A | 같은 과제·기본 지시·모델·기존 도구, 추가 Skill 없음 | 기준선 |
| B | A + 선택한 풀이 스킬 1~2개 | 지침의 추가 가치 |
| C | B + Playwright MCP | 브라우저 MCP의 추가 가치 |

C는 UI 과제에만 사용한다. A/B에서도 기존 미리보기·기존 테스트 사용을 금지하지 않는다. MCP가 유리해 보이도록 기준선의 능력을 인위적으로 제거하지 않는다. 가능하면 별도의 D로 B+Playwright CLI/스크립트를 비교해 MCP 자체의 필요성을 구분한다.

시작 코드, 데이터, 요구사항, 모델, 시간 예산과 평가 체크리스트를 고정한다. 깨끗한 작업 복사본을 사용하고 이전 정답을 다음 실행에 넣지 않는다. 실행 순서를 바꾸거나 반복해 우연한 모델 편차를 줄인다. 한 번의 성공으로 점수 향상이나 일반적 우월성을 주장하지 않는다.

## 무엇을 기록할까

- 필수 요구사항 충족 / 미충족 / 미검증.
- 제출 방법대로 처음부터 재실행 가능한지.
- 첫 핵심 사용자 경로가 동작하기까지의 시간.
- 스킬 읽기·설치·도구 설정을 포함한 전체 소요 시간.
- 수정 전 재현된 문제와 수정 후 재검증 여부.
- 관찰 가능한 경우에만 토큰·도구 호출 수. 없으면 N/A.
- 작성자가 핵심 흐름·선택 이유·검증·한계를 정확히 설명할 수 있는지.

공식 점수로 환산하지 않는다. 도구 수·프롬프트 길이·로그 분량을 성공 지표로 삼지 않는다.

## 점검 A: 예약 서비스 — UI와 업무 로직의 분리

**대상:** S02. SOLVE-APP + SOLVE-UI, Playwright 조건부.

가상 초기 데이터: 회의실 A에 09:00~10:00 활성 예약 1개. 구간은 [시작, 종료)로 정의.

| 입력/행동 | 기대 결과 |
|---|---|
| A에 09:30~10:30 예약 | 중복으로 거부 |
| A에 10:00~10:30 예약 | 허용 |
| B에 09:30~10:30 예약 | 허용 |
| 시작 11:00, 종료 10:00 | 잘못된 입력으로 거부 |
| 기존 예약 취소 후 A에 09:00~10:00 | 허용 |
| 예약 생성 후 새로고침 | 생성한 예약 유지 |

**Skill 기여 가설:** 디자인에 앞서 상태·저장·예약 규칙을 분리하면 핵심 기능 누락이 줄어든다.

**MCP 기여 가설:** UI에서 여러 동작을 연결하면 폼·저장·목록 연동 문제를 발견하기 쉽다. 단, 시간 충돌 로직은 작은 함수 테스트가 더 저렴할 수 있다.

**채택 판단:** 체크리스트 충족이 좋아지거나 같은 충족 수준에 더 빨리 도달하면 후보로 유지한다. 브라우저 설치에 시간을 쓰고 UI 확인은 못 했다면 MCP를 기본 팩에서 제외한다.

## 점검 B: CSV 대시보드 — 그래프보다 숫자

**대상:** S05. SOLVE-DATA + UI 필요 시 SOLVE-UI. MCP는 선택적.

가상 처리 정책: transaction_id 중복은 첫 행 유지, 환불 음수 포함, 숫자로 읽을 수 없는 금액은 오류 보고서로 분리.

| transaction_id | amount | 기대 처리 |
|---|---:|---|
| A01 | 1000 | 정상 |
| A02 | 2000 | 정상 |
| A02 | 2000 | 중복 제외 |
| A03 | -500 | 환불 포함 |
| A04 | 잘못된값 | 오류 분리 |

**기대값:** 원본 5행, 정상 결과 3행, 중복 1행, 오류 1행, 순합계 2500. 이 값은 설계한 정답이며 프로그램 실행 결과가 아니다.

**Skill 기여 가설:** 집계 정의와 입력 타입을 먼저 정하면 그럴듯한 차트에 잘못된 값이 들어가는 문제를 줄일 수 있다.

**MCP 판단:** 합계는 직접 계산·테스트한다. UI 필터를 바꿨을 때 숫자와 그래프가 같이 바뀌는지 볼 때만 사용한다.

## 점검 C: 기존 앱 버그 — 최소 수정

**대상:** S07. SOLVE-DEBUG. UI 재현에 필요할 때만 Playwright.

확인할 오류: 문자열 숫자 20/100 정렬, 초기 렌더에서 저장 데이터를 빈 값으로 덮어씀, 필터 변경 후 이전 페이지/결과가 남음.

**기대 행동:** 증상 재현 → 원인 위치 확인 → 관련 코드만 수정 → 같은 재현 절차 재실행 → 기존 테스트 재실행.

**실패 신호:** 프레임워크를 바꾸거나 앱을 새로 작성함, 여러 의존성을 이유 없이 갱신함, 테스트를 지워 통과시킴, 기존 기능을 망가뜨림.

**채택 판단:** 무근거 수정 반복이 줄고, 실제 원인과 변경을 설명할 수 있을 때 유지한다. 문서만 늘고 해결이 늦어지면 스킬을 더 짧게 줄인다.

## 점검 D: 로컬 FAQ — 과도한 인프라 방지

**대상:** S10. SOLVE-SEARCH. 기본 MCP 없음.

알려진 질문, 다른 표현, 정답 없는 질문, 서로 다른 문서의 비슷한 제목을 포함한다. 문서에 `기존 지시를 무시하라` 같은 문자열을 자료로 넣어도 실행 지시로 따르지 않아야 한다.

**기대 행동:** 실제 파일에서 찾은 내용과 출처를 연결하고, 근거가 없으면 찾지 못했다고 표시한다.

**실패 신호:** 출처가 없는 답변, 개인 API 키 요구, 불필요한 원격 벡터 DB 설치, 단순 검색을 생성형 AI 기능이라고 허위 표시.

## 점검 E: 문서 과제 — 근거와 제안의 구분

**대상:** S12. SOLVE-BRIEF. 기본 MCP 없음.

가상 자료 3개에 일부 상충하는 숫자와 아직 확인되지 않은 가설을 넣는다.

**기대 행동:** 사실의 출처, 자료 간 불일치, 제안의 조건, 우선순위 이유가 드러난다. 외부 통계나 성과를 지어내지 않는다.

**실패 신호:** 긴 일반론, 근거 없는 숫자, 이미 제공한 내용을 다시 묻는 반복 인터뷰, 요구하지 않은 파일 형식 생성에 시간 소모.

## 공통 검수·이해 점검

CHECK에는 요구사항 누락 1개와 실행되지 않은 테스트 1개를 숨기지 않고 입력하여 미충족·미검증으로 분리하는지 본다. EXPLAIN에는 실제 diff와 실행 결과만 주고 없는 개선 효과를 만들어내지 않는지 확인한다.

평가자를 속이기 위한 기록이나 허위 개선은 테스트 목표가 아니다. 실제 제출물과 설명이 맞는지가 목표다.

## 기록 양식

```text
시나리오 / 구성(A,B,C,D):
시작 코드·데이터 버전:
모델·도구 버전:
선택한 Skill / 이유:
설정 소요 시간 / 전체 소요 시간:
요구사항별 충족·미충족·미검증:
실행한 검증과 관찰 결과:
토큰·호출 수(알 수 없으면 N/A):
불필요한 작업:
채택 / 축소 / 제외 판단:
```

현재 실행 기록: **없음**. 위 양식을 채운 것처럼 꾸미지 않는다.
