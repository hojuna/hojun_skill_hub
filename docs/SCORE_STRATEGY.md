# 고득점을 목표로 한 작업 전략

## 확인된 공개 방향과 우리 전략을 구분

[Cofa 공식 공개 페이지](https://www.getcofa.com/ko/probe)는 결과물, AI 대화·도구 설정·검증 기록과 실제 구현에 부합하는 사후 설명을 함께 살핀다고 설명한다. 기술·의도·인지라는 평가 관점을 소개하지만, 이 문서가 해당 시험의 비공개 배점표나 채점 함수를 안다는 뜻은 아니다.

아래는 공개 방향에 맞춘 준비 제안이다. 특정 점수, 순위, 도구 사용 가산점은 주장하지 않는다.

## 기본 전략

**작동하는 필수 기능 → 실패 조건 처리 → 실제 검증 → 근거 있는 개선 → 본인이 설명 가능한 제출물.**

쉬운 과제라면 어려운 기술을 붙이기보다 빠뜨리기 쉬운 요구사항을 끝까지 완성하는 데 집중한다. 이것은 가산점이 확인됐다는 뜻이 아니라 주어진 요구를 충실히 만족시키기 위한 전략이다.

## 1. 문제를 구현 체크리스트로 바꾼다

과제의 사용자, 해야 할 행동, 입력·출력, 저장 요구, 실행·제출 방법을 짧게 추린다. 필수와 선택을 분리한다. 문서에 없는 배점이나 요구사항을 만들지 않는다.

불명확한 규칙이 구현을 바꾸는 경우에만 허용된 담당자에게 질문한다. 예를 들어 공유 예약 서비스인지 단일 사용자 프로토타입인지에 따라 저장 방식이 달라진다. 규칙이 이미 적혀 있으면 다시 묻지 않는다. 답을 받지 못하면 가정과 남은 불확실성을 기록한다.

## 2. 첫 구현은 핵심 경로를 끝까지 연결

예약 앱은 폼→입력 검증→예약 규칙→저장→목록 갱신까지 먼저 만든다. 대시보드는 파일→정제 정책→집계→화면까지 연결한다. 이후 필수 조건을 넓힌다.

화면 전부를 먼저 꾸미거나 계획서·에이전트 구성만 만들다가 실제 실행이 늦어지는 상황을 피한다. 기존 프로젝트와 실행 방식은 우선 유지한다.

## 3. AI 지시는 결과·범위·확인 조건을 포함

가상 예약 과제의 예:

```text
기존 프로젝트와 실행 방식을 유지해 예약 생성·목록·취소를 먼저 연결해줘.
겹치는 활성 예약은 거부하고 종료 시각과 다음 시작 시각이 같은 예약은 허용해야 해.
새로고침 후에도 데이터가 유지돼야 해.
구현 후 정상 생성, 중복 거부, 취소 후 재예약, 새로고침 유지의 실제 결과를 알려줘.
외부 서비스나 새 인증 기능은 추가하지 마.
```

이는 모든 문제에 붙이는 고정 프롬프트가 아니다. 실제 과제의 완료 조건에 맞게 바꾼다. 스킬 이름 나열이나 장문의 사고 과정 출력보다 명확한 작업 범위를 우선한다.

## 4. 검증은 구현 중에, 최종 검수는 짧게

정상 입력 1개, 중요한 잘못된 입력, 저장·계산·상태의 핵심 조건을 우선 확인한다. 모든 종류의 테스트를 다 붙이는 것이 목적은 아니다.

예: 중복 예약이 통과했다면 재현 입력과 실제 결과를 근거로 원인을 찾고, 수정 후 같은 입력을 다시 실행한다. 단위 테스트·빌드·브라우저 동작 확인은 서로 증명하는 범위가 다르다.

검증 수·로그 길이를 부풀리지 않는다. 기존 테스트를 지우거나 오류를 숨겨 성공처럼 만들지 않는다.

## 5. 개선은 실제 발견에서 나온 것만

개선은 필수 동작의 오류 수정, 빠뜨린 상태 처리, 더 명확한 오류 메시지, 요구에 맞는 사용성 보완 등일 수 있다. 반드시 어려운 성능 최적화일 필요는 없다.

`문제 발견 → 변경 → 다시 확인한 결과`를 짧게 남긴다. 개선 전후를 측정하지 않았다면 성능 향상 수치를 쓰지 않는다. 일부러 결함을 만들어 개선 사례를 연출하지 않는다.

## 6. 문서는 최소한의 증거로 충분

실제 과제에 별도 문서 요구가 있으면 그 요구를 따른다. 없다면 내부 작업 노트는 목적, 완료 조건, 중요 선택, 실행 근거, 남은 한계 정도면 된다. 파일·명령·관찰 결과가 대응되어야 한다.

사후 설명 준비는 다음 질문에 본인 말로 답할 수 있는지 확인한다.

- 사용자가 입력하면 어떤 처리를 거쳐 어디에 저장·출력되는가?
- 왜 이 방법을 골랐고 대안과 어떤 차이가 있는가?
- 무엇을 실제로 확인했으며, 무엇은 확인하지 못했는가?
- 실제로 수정한 문제와 다시 확인한 결과는 무엇인가?
- 남은 한계는 무엇인가?

AI 사용이 허용되지 않는 후속 단계에서는 AI를 호출하지 않는다. 참고 파일 접근 가능 여부도 실제 안내를 따른다.

## 시간 배분 제안: 작업 180분을 가정할 때

| 구간 | 목적 |
|---|---|
| 0~10분 | 요구·기존 코드·실행 방식 확인, 풀이 스킬 선택 |
| 10~135분 | 핵심 기능과 나머지 필수 기능 구현, 중간 실행·수정 포함 |
| 135~155분 | 중요한 실패 조건과 요구사항 누락 검수 |
| 155~170분 | 필요한 제출 문서 정리, 본인 이해 확인 |
| 170~180분 | 재실행·저장·경로·제출 확인 |

이것은 개인 준비용 배분안이지 공식 시간표나 최적 배분에 대한 실험 결과가 아니다. 문제 수·배점·난도에 맞게 조정한다. 검수를 끝까지 미루라는 뜻도 아니다.

여러 독립 과제라면 먼저 각 과제의 필수 산출물과 배점을 확인한다. 한 과제의 선택 기능을 꾸미기 전에 다른 과제의 필수 기능을 확보한다. 구현 과제 수와 사후 설명 문항 수를 같은 것으로 단정하지 않는다. 여러 에이전트 병렬 작업도 환경 지원·파일 소유권·자원 여유가 확인된 경우에만 고려하고 기본값으로 두지 않는다.
